# プロセス分析: 自律ループモード vs 対話形式

- 作成日: 2026-08-20
- 対象A（自律ループモード）: `D:\claudeProject2`（本プロジェクト。全6工程完了）
- 対象B（対話形式）: `otherproject\claudeProject`（同一題材・GitHub公開まで完了）
- 目的: 同一題材（15×15五目並べ・Python/tkinter）を異なる開発方式で実施した2プロジェクトを突き合わせ、対話形式の方が可読性・品質で優れ、トークン消費が少なかった理由を特定し、自律ループモードの改善につなげる

本レポートの改善提案は、`waterfall-dev-workflow`スキル（`~/.claude/skills/waterfall-dev-workflow/references/`）の`claude_md_template.md`・`review_rubric.md`・`loop_mode.md`に反映済み（「6. 汎用設定への反映」参照）。プロジェクト固有の知見のうち汎用化できる部分をユーザー設定へ反映する運用（過去のQA記録に基づく）に従った。

## 1. 結論（サマリー）

- 両プロジェクトのコード規模・要件数はほぼ同等で、開発者としての実力差ではない。差は**同じ情報を複数箇所に手で重複記載させ、レビューサブエージェントがその同期漏れを毎ラウンド検出し続ける**という、自律ループ側にだけ存在する構造的な問題に起因する。
- 自律ループの全111コミット中、レビュー記録42件・指摘対応34件の計76件（約68%）が指摘往復に費やされている。その大半は内容の誤りではなく、要件ID・関数ID・テストIDが本文／トレーサビリティマトリックス／テストコードdocstringの3箇所で食い違っているという転記漏れの指摘だった。
- 同一指摘が最大3ラウンド連続で再発するケースがあった（テスト工程COMP-02）。開発サブエージェントが毎回コールドスタートし、修正箇所の横展開ができていないことが原因。
- 対話形式は同じ指摘密度でも「ユーザーが指摘を一括で出す→Claudeが一括で全対応→承認」で毎回一発収束しており、「ラウンド」という概念自体が存在しなかった。
- **設計資料そのものの可読性にも明確な差があった**（当初の分析で見落としていた観点）。対話側はMermaid図（アーキテクチャ図・シーケンス図）と、文書情報表（版数・改訂履歴）を備え、対応要件IDは「簡潔な一覧＋非自明なものだけ説明」の形式。自律ループ側はテキストのみの依存関係表現で、対応要件IDを1文に全件詰め込む密な書き方になっていた。行数だけ見ると自律ループ側のcomponent_design.mdの方が短い（161行 対 236行）が、これは説明を削ったのではなく図解の代わりに密な文章で押し込んだ結果であり、実質的な可読性はむしろ低い。

## 3. 往復が膨らんだ4つの構造要因

### 3.1 トレーサビリティ情報を3箇所に手で重複記載させている

要件ID・関数IDの対応関係を、①各工程の成果物本文、②`traceability_matrix.md`、③テストコードのdocstring、の3箇所すべてに人手で書かせる運用になっていた。1箇所を直しても残り2箇所への反映漏れが構造的に発生し、レビューサブエージェントはこの不一致を毎ラウンド検出し続けた。

典型例（`docs/review_log.md`より、テスト工程COMP-02）:

> **R1** — `tests/test_game_logic.py`のTEST-06/07 docstringに`CON-02`の記載漏れを指摘
> **R2** — 「ラウンド1で修正したはずが、テストコード側のdocstringは`REQ-04 / FUNC-05`のまま未更新」と再指摘
> **R3** — 「ラウンド2で直したはずが、実際にはtest_specification.md側にしか反映されておらずdocstringは依然未更新」と三度目の指摘

同種の反映漏れが、同じラウンド内でREQ-07・FUNC-04・境界値注記の削除など計5系統も並行発生していた。

### 3.2 「重大」判定のデフォルトバイアスが往復を強制する

`review_rubric.md`（改訂前）は「判断に迷う指摘は軽微側に倒さず重大側に倒す」と定めていた。これ自体は品質担保の意図だが、共通観点の「該当するIDがtraceability_matrix.mdに反映されているか」という形式的チェックとかけ合わさると、内容に矛盾のない単なる転記漏れまで機械的に「重大」へ倒れ、再レビューが強制されていた。関数設計・テスト工程のレビュー記録では、指摘の過半数が「対応要件ID欄への追記漏れ」の類だったが、多くが重大判定を受けていた。

### 3.3 開発サブエージェントが毎回コールドスタートし、横展開できない

指摘1件（またはラウンド1回分）ごとに新規の開発サブエージェントが起動される。渡されるのは「この箇所を直せ」という局所的な指摘であり、「同じ情報が他に何箇所書かれているか」を能動的に洗い出す指示がワークフローに組み込まれていなかった。結果、指摘された1箇所だけ直して完了報告し、同じ情報を持つ別の場所（テストdocstring等）が未修正のまま次ラウンドに持ち越された。

### 3.4 「些細でも全て指摘」という網羅性最優先方針

`review_rubric.md`冒頭は「指摘は些細なものでも省略せず全て挙げること」と明記していた。3.1〜3.3と組み合わさると、1ラウンドに大量の形式的指摘が積み上がり、往復のたびにコミット・トークンを消費する。対話形式では、ユーザーが「これは今直さなくていい」と直感的に取捨選択できる分、指摘密度そのものが抑制されていた。

## 4. 設計資料の可読性差（追加分析）

当初の分析では往復回数・文字数の定量比較に留まり、設計資料そのものの**質的な**可読性差を見落としていた。両プロジェクトの`component_design.md`・`function_design.md`を実際に読み比べた結果、以下の差が明確に確認できた。

### 4.1 アーキテクチャ図・データフローの表現方法

- **対話形式**: `component_design.md`にMermaidの`flowchart`でレイヤー構成図、`sequenceDiagram`で「石を置く操作」「リセット操作」の2つのデータフローを図示している。分岐（対局終了済み／既着手／勝利成立／引き分け／継続）を含む処理の流れが、`alt`/`else`のシーケンス図として一読で追える。
- **自律ループ**: 依存関係をコードブロック内のテキスト（矢印記号による手書きの疑似図）で表現しており、図としてレンダリングされない。分岐を伴うデータフロー図（シーケンス図相当のもの）は存在せず、処理の流れはコンポーネント詳細の責務説明（プレーンな段落）から読み取る必要がある。

### 4.2 「対応要件」欄の書き方

- **対話形式**: 対応要件IDをまず`REQ-04, REQ-05, REQ-10, REQ-13, NFR-05`のような簡潔な一覧で示し、対応関係が自明でないIDについてのみ、箇条書きで理由を補足する（例:「REQ-10（引き分け判定）: 『盤面が全て埋まっているかの判定』はGameStateが引き分けを判定する際の直接の根拠となるため、Boardの責務として本要件に対応する」）。
- **自律ループ**: 1つのコンポーネントの対応要件を「REQ-01（盤面状態の保持）、REQ-02（初期状態が全マス空であること）、REQ-04（石の配置）…」のように、全IDに逐語的な括弧書き説明を付けて1文（COMP-02の例では16個のID）に詰め込んでいる。理由を全件均等に書こうとするほど文が密になり、一覧性・可読性を損なっていた。この書き方は、`review_rubric.md`の「上流工程のIDとの対応関係が明記され、矛盾がないか」という指摘基準に対して機械的に説明を積み増した結果と考えられ、3章の構造要因（特に3.2・3.4）と根を同じくする。

### 4.3 文書としての体裁

- **対話形式**: `component_design.md`・`function_design.md`ともに冒頭に「文書情報」表（プロジェクト名・版数・作成日・対象）と「改訂履歴」表（版数ごとに何を・なぜ変更したか）を備えている。レビュー指摘への対応履歴が本文に埋没せず、版を追って追跡できる。
- **自律ループ**: この種の文書メタ情報表を持たない。改訂の経緯は`review_log.md`という別ファイルを参照しないと分からない。

### 4.4 総括

行数だけを見ると自律ループ側の`component_design.md`はむしろ短い（161行 対 236行）。しかし短いのは説明を絞り込んだからではなく、**図解すべき内容を密な文章で代替した結果**であり、実質的な可読性は対話側の方が高い。これは3章で述べた「機械的な網羅性チェックが、内容よりも形式的な完全性を優先させる」構造要因が、文章密度という形でも表れた例と言える。

## 5. 対話形式が実際にやっていたこと

`otherproject/docs/qa_log.md`を見ると、コンポーネント設計・関数設計のいずれも「ユーザーが指摘3〜4件をまとめて出す→Claudeが全件を1回の修正でまとめて対応→承認」という一発収束のパターンで進んでいる。これは人間のレビューが優れているからというより、次の2点が効いている。

**対話形式の勝因**
- 指摘者（ユーザー）とレビュー対象の文脈が最初から最後まで同一で、「さっき直したはず」の記憶が途切れない
- 指摘をまとめて一括で出し、修正側も一括で全対応してから再確認する「バッチ処理」になっている
- 形式的な整合性より、実質的な矛盾・実装可能性（例:「MoveResultに石の色フィールドが無くFUNC-20が実装不能」）を優先して拾っている

**自律ループの摩耗点**
- ラウンドごとに独立したサブエージェントが起動し、前回の文脈を都度再構築している
- 1指摘ずつ検出→報告→修正のサイクルを回すため、まとめて直せば1往復で済む内容が複数往復に分割される
- 形式的なID転記漏れが「重大」判定され、実質的な設計欠陥と同列にエスカレーションを要求する

## 7. 変えなくていいもの

自律ループの全てが劣っているわけではない。無人での長時間稼働、要件網羅性の機械的な取りこぼし検出（実際、テスト工程完了時にCOMP-01用テストモジュールの計画漏れを検出できたのはこの網羅性チェックのおかげだった）、配布後に発覚したGUI不具合（石の交点配置・視認性）を受けてレビュー観点を即座に自己改訂できた点は、対話形式にはない強みである。今回の提案は「網羅性を捨てる」のではなく、「同じ情報を1箇所でしか管理しない」ことで、その網羅性チェックを機械的・低コストに保つ方向の変更である。

## 8. 分析手法の限界・追加で分かったこと

初版レポート公開後、指摘を受けて確認したところ、分析手法自体に見落としがあったため訂正する。

### 8.1 otherprojectのgit履歴は比較に使えなかった（訂正）

`otherproject/claudeProject`には独自の`.git`が存在しない。このディレクトリ内で`git log`等を実行すると、gitは親ディレクトリを遡って`D:\claudeProject2\.git`（本プロジェクト自身のリポジトリ）を見つけて動作するため、**「otherprojectのコミット数・コミット履歴」として提示していた数値は、実際には本プロジェクト自身のgit履歴だった**（`git -C otherproject/claudeProject rev-parse --show-toplevel`で`D:/claudeProject2`が返ることで確認済み）。当初レポートの「総コミット数111/111が偶然一致」という記述は誤りで、削除・訂正した。

一方、ドキュメント行数・テストコード量・`qa_log.md`の内容・設計書の質的比較など、**Readツールでファイルを直接読んで行った比較はすべて実ファイルの内容そのものであり、この問題の影響を受けない**（otherprojectはgit管理下になくても、ファイル自体は実在し中身も別プロジェクトのものだった）。したがって3〜5章の構造要因分析・可読性分析・「対話形式が一発収束していた」という結論自体は影響を受けないが、コミット数を根拠にした主張は今回の訂正版から除いた。

教訓: 複数プロジェクトを比較する分析では、対象ディレクトリに独立した`.git`が存在するかを`git rev-parse --show-toplevel`等で先に確認すべきだった。`cd`と`git log`が正常終了したことだけで「意図したリポジトリを見ている」と判断したのが誤り。

### 8.2 GUI不具合の回避を実装コードで確認（追加の裏付け）

4章で述べたGUI不具合（石をマス中央でなく交点に描画すること、白石の視認性）について、自律ループ側は配布後に発覚し事後修正したが、対話側がこれをどう扱っていたかは未確認だった。`otherproject/claudeProject/src/board_canvas.py`を直接確認したところ、座標変換関数が`MARGIN + col * CELL_SIZE, MARGIN + row * CELL_SIZE`（マス中央ではなく格子の交点座標）を返し、石の描画も`outline=STONE_OUTLINE_COLOR`という専用定数（塗りつぶし色の使い回しではない）を使っていた。つまり対話側は**この2つの不具合を最初の設計・実装の時点で回避できていた**。ただしこれが「対話形式というプロセスそのものの効果」なのか「実装した開発者・セッションが五目並べの慣習を最初から意識していただけ」なのかは、この1件の比較だけでは切り分けられない。

### 8.3 残る不確実性・注意点

- **サンプル数が1組しかない**: 本レポートの構造要因分析は、同一題材の2プロジェクトという1組の比較に基づく仮説であり、統計的に検証されたものではない。`review_rubric.md`等への反映は「今後の自律ループ運用で往復回数が実際に減るかを観察する」ことで検証する必要がある。次にこの方式を使うプロジェクトでは、`docs/review_log.md`に指摘の重大/軽微内訳を記録する運用が既にあるため、改訂前後で往復回数・「ID転記漏れ由来の指摘」比率を比較できる。
- **両プロジェクトの前後関係が未確認**: otherprojectの`qa_log.md`・本プロジェクトの`docs/qa_log.md`は、いずれも要件定義の承認日を内部記録上「2026-08-11」としており、同日に並行して着手された可能性が高いが、断定はできない（8.1の理由でgit履歴からの裏付けができないため）。もし一方が他方の後に行われ、開発者（または対話しているClaude自身）が前の経験を踏まえていたなら、可読性・品質の差の一部は「プロセスの違い」ではなく「2回目だから」という学習効果に起因する可能性がある。
- **「重大」判定を緩めたことによるリスク**: `review_rubric.md`に加えた「内容面の矛盾を伴わないID転記漏れは軽微に固定する」という例外規定は、往復削減には有効なはずだが、レビューサブエージェントがこの判断を誤り、実質的にスコープが食い違うケースまで「単なる転記漏れ」と誤判定して見逃すリスクを理論上伴う。共通観点の他項目（曖昧な表現・スコープクリープのチェック等）と重複しているため実害は限定的と考えられるが、次回以降のレビュー結果で「軽微に倒したことで見逃した」事例がないか注意して観察する必要がある。
